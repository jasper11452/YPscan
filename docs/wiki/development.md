# 开发与验证

## 先定位层次，不要把每个问题都修成提示词问题

最短证据链是：**用户完整有效需求 → 本次工具参数 → 工具真实返回 → 模型下一步动作**。样本须脱敏，保留顺序和关键条件。

| 证据                            | 优先检查                                          |
| ------------------------------- | ------------------------------------------------- |
| 用户已提供，解析结果漏字段      | 解析与现有复核是否正确恢复明确值，不先重问用户    |
| 模型发出的参数错误              | 参数生成、归一化和必要的边界校验                  |
| 参数正确，后端执行不同          | Provider 实际执行证据，不靠加提示词或盲目重跑解决 |
| Hook 已提示等待，模型仍调用下游 | 指令是否送达、冲突、注入时机及模型行为            |
| 工具结果正确，但弹窗未显示      | 宿主渲染和载荷契约，不先修改业务流程              |

拿不到关键证据就说明未知。声明根因修复前，至少能解释原来哪里错、补丁为何有效、怎样判定无效。正式修复覆盖已证实的受影响路径；一次只改变一个可证伪因素，并不等于只许改一个文件。

## 奥卡姆剃刀：没有必要性证据就不增加

- 加规则前先搜 Skill、工具卡、Hook 和 Spec：已有规则未生效时，先查冲突和执行路径，不再复制一条“必须/禁止”。
- 确定性参数、文件来源与结果关联由程序处理；语义理解、澄清和解释由模型处理；任务状态、机构匹配、去重与幂等由 Provider 处理。不为方便修改而把责任都堆到 Hook。
- Hook 优先给当前阶段和动态参数，不用每轮重复整条流程来修补局部问题。
- 不为假想需求新增状态机、缓存、全局门禁、文档生成框架或兼容分支。兼容实际响应时保留脱敏样本和保留理由。
- 无效的试探性改动只撤销本次可精确分离部分；不能把未证实有效的改动当作保险留在主线。
- 不按文件行数决定重构，不按测试数量决定删除遗留代码。先证明其维护成本和删除边界。

## 验证分三层，不能互相冒充

1. **代码层**：lint、typecheck、单元测试、smoke。字符串断言证明指令生成正确，不证明模型遵守指令。
2. **模型行为层**：检查调用顺序、参数、停止位置和用户可见结论，不强求固定措辞。模型变化、上下文变化也可能导致回归。
3. **真实宿主层**：验证弹窗渲染、字段页提交后的恢复、文件交付和必要平台集成。模拟响应不能替代这一层。

修交互问题时优先把真实失败转成可重复样本；现有条件无法自动化时记录可复现步骤、实际轨迹和限制，不声称已经通过。工程验收继续使用 [Review Checklist](../review-checklist.md)。

### 首批行为样本与判据

| 场景                                | 通过标准                                             |
| ----------------------------------- | ---------------------------------------------------- |
| 原文“返点25%以上”，解析 rebate=null | 使用明确的最低返点，不要求用户重答同一值             |
| 字段选择返回 URL                    | 原样展示并结束本轮；手动拓展、打分等下游调用次数为 0 |
| 需求粉丝10万，实际搜索参数50万      | 指出参数偏差，不称为放宽成功，不承诺盲目重跑能修复   |

先使用固定脱敏响应和隔离工具接口，不发送企微、不落真实需求、不上传文件。记录代码基线、模型标识、宿主版本、工具 schema/Provider 环境、输入、完整工具轨迹、判据与结果。尽量固定影响结果的运行参数。

每个场景先跑 5 次作为低成本筛查；5 次通过不是稳定性证明。出现波动时，在扩大样本前确定重复次数和通过阈值，不能只挑成功的一次。当前仓库 CI 只执行代码层检查；本页是行为回归方法，不代表模型跑批框架已实现。

## 消融实验：一次拿掉一个因素，判断它是否有用

只在隔离副本或可回退的本地环境试验，保持输入、响应、模型和其他条件尽量一致：

| 版本        | 唯一变化                                        | 要回答的问题           |
| ----------- | ----------------------------------------------- | ---------------------- |
| A：基线     | 无                                              | 当前失败能否重复出现？ |
| B：消融     | 仅去掉该场景重复静态提醒，保留 Skill 和动态参数 | 重复提醒帮助还是干扰？ |
| C：候选修复 | 相对 A 只改证据指向的一处                       | 最小补丁能否解决失败？ |

B、C 分别与 A 对照，不把删提醒与新修复混在同一实验中。记录样本数、成功/失败数和异常轨迹。

- A 不失败：先补足真实上下文，不猜测修复。
- B 更差：恢复；B 无明显变化：只能证明本组样本未体现作用，补相邻场景验证后才考虑删除。
- C 解决原失败且相邻路径不退化：保留；C 无效：撤回可分离的候选补丁，重新定位，不叠加保险机制。
- 文件来源、平台隔离、授权和上传边界不是随意消融的冗余提示。不得在真实业务中关闭安全控制做实验。

## 外部契约与安全

- 遇到契约问题，核对当前环境 live schema 和真实响应。保存脱敏样本并标明环境；不要把某个 Provider 版本的行为当永久事实，也不要让普通单元测试连接生产服务。
- OSS 凭据不入 Git 只解决仓库暴露问题，不解决客户端分发风险。安装包接收者应视为能提取凭据；核查权限、有效期、分发范围和轮换，不记录秘密本身。
- 已分发的长期共享凭据若可读取无关对象、覆盖或删除数据，应优先制定受授权的替换与轮换方案。先看现有权限策略能否收窄风险，必要时再考虑临时凭据或服务端上传；不在缺乏证据时擅自吊销或增加整套服务。
