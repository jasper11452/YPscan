## 1. 结论与实施选择

### 1.1 三个可复现缺陷与一个待确认影响的差异

| 编号 | 位置 | 问题与影响 |
| --- | --- | --- |
| D1 | `parse` / `score_json` / `score_retry_json` / `final` | 单达人净价条件可能被解析提示词排除、被普通报价核验覆盖，最后又因“返点”子串被丢弃；只改末端会暴露错误 PASS/FAIL |
| D2 | `review_json` | “不能确认满足预算”被识别为肯定，错误触发 `review_conflict`，整份复核降级为初评 |
| D3 | `review_json` / `final` | “未提供口播样本，无法判断表达能力”被当成无证据能力主张删除，交付缺失原因说明 |
| D4 | 四个评分/复核/交付代码节点 | 证据别名集合与接受的值类型不一致已确认；真实 payload 是否触发、后果方向仍未知，不能直接扩表或删表 |

### 1.2 默认路径：一次完整候选，按缺陷分别验收

1. **M0 冻结基线与反例**：本地核对节点、调用关系、回放加载源；D4 普查独立进行，不阻塞 D1–D3。
2. **M1 / P0 修复 D1**：条件作用域与价格口径成套贯通解析、首次/重试评分和 `final`，不新增公式引擎。
3. **M2 / P1 修复 D2–D3**：复用逐条件结果，增加复核 verdict 与可校验的证据缺口；不先维护一套临时中文词表再重做。
4. **M3 验证与发布**：P0/P1 各自保留基线对照，组合候选通过后默认只发布一次评分工作流。实施与外部操作须在用户授权范围内；本次文档优化不启动实施。

临时词表补丁只作为明确要求紧急缓解时的备选，不是 P1 前置步骤。D4 和搜索实验有独立退出条件，不以“调查尚未完成”拖住已证实缺陷的修复，也不把未完成项写成已修复。

### 1.3 保持的业务规则

硬条件、偏好和交付规则分层；PASS / FAIL / UNKNOWN 语义；UNKNOWN 只标待确认、不单独淘汰；可信硬条件 FAIL 阻断。类型标准、梯度候选池（N=5→15）、首批 `min(20,N)`、每批上限 20、排序、0 分排除、评分权重/阈值、搜索价格只扩展一次均保持现有契约。

纠正错误判定允许改变个别达人的推荐结论，不能以“推荐名单完全不变”验收。不得猜测返点比例、净价公式或原生字段名。

## 3. 缺陷矩阵

### 3.1 D1：`final` 的 `NON_CREATOR_WORDS` 子串过滤

代码（`final`，行号为当前候选导出中的行号）：

```python
 61| NON_CREATOR_WORDS = ('返点', '综合分', '提报截止', '提交截止', '报名截止', '截止时间')
 64| def _creator_side(label):
 65|     text = label if isinstance(label, str) else ''
 66|     return not any(word in text for word in NON_CREATOR_WORDS)
```

两个调用点，命中即 `continue`，条件被**整条丢弃**：

```python
228|             if not _creator_side(label):      # must_have / must_not 循环
229|                 continue
243|         if not _creator_side(label):          # secondary_conditions 循环
```

- 判定方式是**子串包含**，不是"整条条件是否属于项目/商务侧"。任何 label 里出现"返点""综合分""截止"等词，无论语义，都被跳过。跳过等于既不 FAIL、也不 UNKNOWN、也不出现在交付文案——这是**丢弃**，不是"过滤后仍有记录"。
- 触发链：解析节点把"返点后到手单价不超过10000元"写入 `must_have` 时，`label` 含子串"返点" → `continue` → 该条件既不进 `hard_failed` 也不进 `pending`，最终表既没有 FAIL 也没有"待确认"，超预算达人仍可被推荐。
- 为什么不能直接删：`parse` 提示词已明确要求"返点、提报截止时间、招募数量/预算属于项目或商务侧条件，不写入 must_have、must_not 或 secondary_conditions"，并要求"must_have、must_not、secondary_conditions 只写单个达人可核验的条件"。也就是说，`_creator_side` 是**对解析模型漂移的代码级第二道防线**，删除它会让项目级条件直接进入达人门禁（回到"综合分不为0 被当硬条件"的老问题）。
- **但 `business` 这一档不能涵盖全部单达人商务价格条件。**"返点后到手单价不超过10000元"针对的是单个达人的实际到手价，是可核验的价格条件，必须保留并参与门禁；它与"提报截止时间""招募数量""总预算"这类项目级条件性质不同。因此第 4.1 节的 `scope` 必须把两者分开，不能合并成 `business`。
- 合成复现（C 级）：上轮用**当时导出的 `final` 节点代码**在进程内做合成复现（审计脚本 `/tmp/dify-audit/falsify-audit-gaps.py`，临时路径，**待移入版本化夹具**）。覆盖 6 个触发词各一条 + 一条不含触发词的对照 + 一条 `secondary_conditions`：`parsed.must_have=[{"id":"H9","requirement":"返点后到手单价不超过10000元"}]`、`scored.constraint_results=[{"id":"H9","status":"FAIL","evidence":"…：同口径核验净价 12000 元"}]`（上游已按同口径核验的 FAIL，**不含任何算式**），期望 `hard_constraint_fail`，当前实际为通过门禁（条件被跳过）；对照条件"到手单价不超过10000元"则正常阻断。真实运行中是否出现过该 label，本轮无样本，记为 D 级。
- **合成前提要说清**：这里的 FAIL 是**上游已经核验并写入 `constraint_results` 的结论**，缺陷是 `final` 把它丢了。**原生报价本身不构成 FAIL 证据**——报价 12000 元只说明报价超限，返点后净价是否超限取决于返点比例；只有报价而基数不明时只能是 UNKNOWN（见 4.2）。


**本次补充复现：只改 `final` 会暴露上游错判。** `tests/fixtures/dify-score-json.py:228-241` 的 `deterministic_checks` 对 `must_have` 中含“单价”的文本统一调用 `_price_check`（行 174 起），没有区分报价与返点后净价；`validate` 行 299-301 再用程序结果覆盖模型结果。本次离线调用该函数：同一条件“返点后到手单价不超过10000元”，只有 `profile.视频报价=12000` 时返回 FAIL，只有 `8000` 时返回 PASS；按本计划两者都应为 UNKNOWN。这是合成代码复现，不代表真实达人触发。P0 必须修复核验与合并路径，不能把现有程序 FAIL 一概称为“同口径可信 FAIL”。

### 3.2 D2：`review_json.has_affirmative` 的否定判定

```python
 45| def has_affirmative(text, words):
 ...
 54|             prefix = text[:index]
 55|             if not re.search(r"(?:不|未|无法|不能|没有)(?:\s|完全|充分|很)*$", prefix):
 56|                 return True
```

正则锚定在目标词**紧邻左侧**，只允许否定词与目标词之间夹空白或"完全/充分/很"。因此"不能确认**满足**预算"里的 `确认` 隔断了 `不能` 与 `满足`，被判定为肯定主张。

调用与后果：

```python
210|     claims_ok = [text for text in texts if isinstance(text, str) and has_affirmative(text, ('符合', '满足'))
211|                  and any(word in text for word in price_words)]
214|     if claims_ok and price_failures:
215|         conflicts.append('复核称价格符合，但程序核验为超上限')
220|     require(not conflicts, 'review_conflict')
```

`require` 抛错 → 该次复核整体失败（`error_kind='review_conflict'`），`final` 侧 `review_status != 'ok'` → 使用 `scored` 初评并在理由末尾追加"整体复核未完成，暂采用初评，需人工复核。"。`review_json` 没有重试节点，一次误判直接降级。

- **放宽"词前若干字符内有任意否定词"不是安全修复。**"不仅满足预算"里的"不"属于"不仅"，"不是不符合预算"是双重否定，两者都会在"任意否定词豁免"下被错误放行，导致真实矛盾漏检。临时词表只能作为有边界的缓解；默认直接实施第 5 节。“不仅满足预算”是保护用例；双重否定是当前漏检的目标用例。
- **本次纠正原计划的事实错误**：`has_affirmative("不是不符合预算", ("符合", "满足"))` 实际返回 False，已有复核校验会漏掉相应冲突；“不仅满足预算”才返回 True。现有 32 项脚本不含该双重否定。旧 P11 应归入目标用例 T6，而非声称当前已正确。
- `business.price` 虽位于 JSON 对象内，值仍是自由字符串，并非 PASS/FAIL/UNKNOWN 枚举；该路径也调用 `has_affirmative`，不能视为已经可靠的结构化判断。

### 3.3 D3：`find_fabrications` / `_strip` 删除缺证陈述

`final` 侧（行 5-6、144-154）：

```python
  5| CLAIM_GUARDS = (('comments', ('跟做', '提问', '追问', '复刻', '粉丝信任', '粘性', '号召')),
  6|                 ('content', ('口播', '表达清晰', '出镜', '讲解流畅', '语速')))
144| def _strip(texts, counts):
145|     kept, removed = [], []
146|     for item in texts:
147|         bad = False
148|         for need, words in CLAIM_GUARDS:
149|             if counts.get(need, 0) > 0:
150|                 continue
151|             if any(word in item for word in words):
152|                 bad = True
153|         (removed if bad else kept).append(item)
```

`review_json` 侧 `find_fabrications`（行 79-90）语义相同，产出"缺少content证据却出现表述：口播"这类问题，`_sanitize` 据此删除条目。

- 触发链：文案里出现"未提供口播样本，无法判断表达能力"，其中含 guard 词 `口播`，而 `counts['content'] == 0` → 该条被删。**这是一条关于"缺证"的陈述，不是关于达人的正面主张**，删除后反而丢失了"为什么无法判断"的信息。
- 删除不是无痕的：`_copy_items`（`final` 行 45-51）把被删项改写成 `'文案校验：已删除缺少证据的表述：' + item` 归入 `diagnostics`，交付列只保留 `kept`；`COPY_DIAGNOSTIC_PREFIXES`（行 41-42）保证这些诊断不出现在用户文案列。修复目标是"不再误删"，不是"让删除可见"。
- **混合句不得放行**：像"未提供口播样本，但口播讲解清晰"这种子句内同时含缺证线索和明确正面断言的句子，仍必须按原逻辑删除。第 5.2 节不得借“缺证”标签放行该正面主张。
- 与 D4 的关系：`counts['content']` 只认 `('正文', '内容', '视频转写', '转写', 'asr')`（`final` 行 137-139），不认 `note_content` / `transcript`。若这些别名确实存在且确有值，计数会偏低、误删会放大；**但这一点尚无证据**，见 3.4。

### 3.4 D4：证据别名与有效值判定不一致

| 字段族 | `score_json` / `score_retry_json` | `review_json.evidence_caps`（行 69-72） | `final._counts`（行 137-139） |
| --- | --- | --- | --- |
| 标题 | `('视频标题','标题','title','note_title')` | `('视频标题','标题','title')` | 不参与 |
| 正文/转写 | `('正文','内容','note_content','视频转写','转写','asr','transcript')` | `('正文','内容','视频转写','转写','asr')` | `('正文','内容','视频转写','转写','asr')` |
| 指标 | `('播放量','点赞量','评论量','转发量','播放','点赞','互动')` | `('播放量','点赞量','评论量','转发量')` | 不参与 |
| 评论 | 不参与 | `('评论原文','评论内容','comment_text')` | `('评论原文','评论内容','comment_text')` |

- **已确认**：四张表不一致（A 级）。**未确认**：这种不一致是否真的造成过错误的证据上限或误删（D 级，真实触发未知）。本文不声称"未验证别名必然虚高上限"——别名表里写了某字段名，只有在该字段**真实存在、有值、且语义相同**时才会计入；否则它不产生任何效果。同理也不能声称删除它们一定会降低上限。
- **无实证时不做别名增删**：没有真实原生 payload 证据时既不能扩表，也不能删表；保留已知行为（现状四张表原样），只做只读普查与差异记录。
- **一致性按节点职责**：`score_json`/`score_retry_json` 负责内容/类型证据上限（标题、指标、正文），两者必须逐项相同；`review_json` 负责复核证据上限，其正文/评论集合应与守卫计数同源；`final` 只做守卫计数（评论、正文），不参与标题/指标，**不要求与 `score_json` 的表逐项相等**。要求的是"同一语义在承担同一职责的节点上取同一集合"，不是"所有节点共用一张大表"。
- **别名之外还有值类型差异**：`tests/fixtures/dify-score-json.py:31-42` 与 `dify-review-json.py` 的 `has_any` 接受非空字符串、数字（含 0）及非空列表/字典；`tests/fixtures/dify-final.py:127-140` 只计非空字符串。即使字段名一致，计数仍可能不同。字段族的有效值语义须连同别名一起核对；真实触发仍未知。
- 历史事实：`score_json` 在基线与首次发布前候选里就已带 `note_title`/`note_content`/`transcript`，而 `review_json`/`final` 一直没有，因此不是"本轮扩表时漏改下游"。

## 4. P0：D1 最小完整修复

### 4.1 解析只表达条件含义

沿用 `id`、`requirement`、`source_quote` 和 `must_have` / `must_not` / `secondary_conditions` 分组，新增最少的语义字段：

| 字段 | 取值与用途 |
| --- | --- |
| `scope` | `creator_objective` / `creator_commercial` / `project` / `delivery`；替代 `final` 的子串过滤 |
| `price_basis` | 价格条件使用 `quoted` / `rebate_net` / `unspecified`；区分普通报价、返点后净价和口径不明，不在非价格条件上强加字段 |

- “返点后到手单价 ≤ X”是 `creator_commercial` + `rebate_net`；“单条报价 ≤ X”是 `creator_commercial` + `quoted`；总预算/截止时间为 `project`，“综合分不为0”为 `delivery`。一条原文混合多种条件时拆成独立 id，原文引用允许重叠。
- 同步 `parse` 与 `parse_retry` 的提示词/结构化输出、两个 `parse*_json` 的严格字段集合/枚举校验。原提示词“返点不写入达人条件”须限定为项目级条件，不能继续排除单达人净价。
- `source_quote` 沿用候选现有的“非空 + 完整有效需求子串”校验；不是另建一份改写需求。不强制把项目/交付规则写入达人数组；若模型输出，依 scope 路由并留诊断。
- 解析不判断某位达人的证据是否充足。删除拟新增的 `verifiability`、`check_kind`、任意 `derivation.formula`；本次没有通用规则引擎的必要性证据。
- 缺 scope、价格条件缺 `price_basis` 或非法枚举均走现有解析重试/失败分支，不默认 creator、不回退子串。**合法空条件集合**仍可评分，不能把“没有硬条件”等同于“解析结构缺失”。

### 4.2 确定性核验留在评分校验节点

`score_json` 与 `score_retry_json` 同步改 `deterministic_checks`、`_price_check` 的适用范围以及结果合并；`final` 只消费已校验结果，不复制第二套数值核验。

| 条件/证据 | 核验结果 |
| --- | --- |
| `quoted`，已有同形式、同单位的报价字段 | 沿用当前确定性比较、别名冲突与缺失规则 |
| `rebate_net`，只有报价，或报价加比例但公式/口径不明 | UNKNOWN；高于/低于净价上限都不能自动判 FAIL/PASS |
| `unspecified`，无法确认应使用哪个价格口径 | UNKNOWN，说明缺口 |
| 原生证据明确给出同口径净价，或完整基数/公式有权威定义 | 只有取得真实字段与语义证据后才增加针对性核验；当前没有证据，不预置公式或字段名 |
| 项目/交付条件 | 不走达人价格/粉丝核验，不因“总预算”等词污染判断 |

`constraint_results` 仍是评分校验后的统一结果。数值结论由程序按真实证据产生；模型写了 FAIL 或 `basis=field` 不构成可信依据。不执行模型生成公式，不假定 `报价×(1−返点比例)`，不拿需求中的最低返点当作达人实际比例。

当前程序核验只遍历 `must_have`。实施时覆盖三个条件组的路由测试；本次不顺带扩展所有禁止/偏好的数值算法。含净价但无核验依据的禁止/偏好同样必须 UNKNOWN；`must_not` 的 status 沿用“是否遵守禁令”，不得把命中禁令解释成 PASS。

### 4.3 `final` 保留条件与既有状态语义

| 条件 | 路由 |
| --- | --- |
| `project` / `delivery` | 不进硬门禁、pending 或交付理由；使用现有 diagnostics 记录过滤的 id、原文、scope，不另建账本 |
| 达人硬条件 FAIL | `hard_constraint_fail`，不推荐 |
| 达人硬条件 UNKNOWN | 进入 `pending_checks`，在理由中标待确认，不单独淘汰 |
| 偏好 FAIL / UNKNOWN | 沿用现有 advisory 和解释，不改为硬淘汰，不新增排序因子 |
| PASS | 不阻断 |

审计必须同时验证“条件未被过滤”和“上游判定口径正确”。T1 的合成消费者 FAIL 测试与 T8 的整条链路测试不可互相替代。

### 4.4 临时缓解仅作备选

若后续明确要求先止损，可单独评估 D1 过滤诊断、D2 有限否定短语或 D3 有限缺证短语；必须写明只覆盖哪些样例、残余误判、回滚方式和退出条件。不得采用“句中出现任意否定词就豁免”，不得让缺证与正面断言混合句整体放行。P1 通过相邻保护用例后删除本次引入且已被替代的临时规则；默认不实施这条支线。

## 5. P1：D2/D3 的最小结构化修复

### 5.1 逐 id 复核，保留校验强度

复用已有 `constraint_results[{id,status,evidence}]`，不另建 `condition_results`。`score*_json` 当前严格校验 id 完整覆盖，继续保留；模型漏项走现有评分重试，不能静默补 UNKNOWN 当成功。UNKNOWN 只表示业务证据不足，不是 schema 出错。

`review` 在原有输出对象上新增 `condition_reviews[{id,verdict,reason}]`，verdict 为 PASS / FAIL / UNKNOWN。只覆盖当前解析出的达人条件，id 必须恰好覆盖、唯一且无外来 id；缺失/非法由 `review_json` 标为复核失败，沿用现有初评降级路径，不新增复核重试节点。合法无达人条件时允许空数组。

- 同 id 的程序 FAIL / 复核 PASS 或程序 PASS / 复核 FAIL，构成正反冲突；沿用 `review_conflict`。偏好冲突只记诊断/advisory，不触发硬淘汰。
- 任一侧 UNKNOWN 不构成正反冲突；**不得清除另一侧已验证的硬 FAIL**。不同 id 的状态不互相比较。
- 门禁消费 `score*_json` 校验后的结果，复核不能凭措辞覆盖确定性事实；主观判断发生分歧时保留证据、说明采用初评，不包装为确定事实。
- 替换 `reason` 等自由文本及 `business.price` 两条极性推断路径。保留现有 `business.price` 的展示兼容，不新增顶层 `price` 状态作为第二权威；价格摘要由逐 id 结论生成，避免结构化 UNKNOWN 与文案“符合预算”矛盾。
- 逐 id schema 只能消除程序靠中文词串猜状态的问题，不能保证模型正确理解双重否定。P10/T6 必须包含模型层测试，不能只手填 verdict 后宣称语义问题全解。

### 5.2 缺证通过受控字段生成可见说明

在 `score` / `score_retry` / `review` 的原有 schema 中增加 `evidence_gaps`，三个读方与 `final` 成套更新。最小对象为 `{kind, condition_ids}`，初始 kind 仅含本次有用例支持的 `missing_content`、`missing_comments`、`unverified_price_basis`；没有必要不预置更多类别。

- 校验 condition id 归属及类别前提：缺正文/评论以已核实字段集合的计数为依据，价格口径缺失以第 4.2 节核验为依据。非条件性的内容缺证允许空 id 列表。模型不能通过自称 `missing_*` 绕过证据核对。
- 不接受任意 `note`、公式或自由字段作为可信缺证输出。最终文案由受控类别生成，例如“未提供口播样本，无法判断表达能力”；原始自由文本仍经过现有主张守卫，不能因为含“无/没有/缺少”而整句放行。
- 评分与复核的合法缺口去重合并；程序已确认缺证时即使复核未给出也保留。说明写入现有用户可见理由/待确认位置，并保留诊断；不增加 Provider Excel 列。
- 内容缺证不是自动淘汰理由，也不自动等于某个硬条件 UNKNOWN。继续按已有证据上限与逐条件结果评分。
- 本阶段保证**受支持类别的真实缺证不会在交付中丢失**；自由文本守卫未覆盖的其他语言误删仍是残余风险。不能声称引入 JSON 后所有文案语义问题都已解决。

### 5.3 成套接口与错误路径

实施前逐项核对提示词、LLM structured-output schema、代码节点严格键集合、变量选择器、首次/重试和 `final` 的实际输入。Dify 整图发布不能替代这项接口检查；在途运行与旧回放样本仍可能属于旧版本，必须按运行版本识别。

非法/空 evidence、解析失败、缺评分、复核失败各走当前已有错误分支。不得把非法 evidence 转为空对象再当正常成功，也不新设“最低档继续”来替代既有错误语义。首次/重试对同一输入应给出相同业务结果，允许 attempt 等诊断差异；不要求整段源码字节相等。

### 5.4 D4 独立证据任务

从本机已有脱敏原生 payload 普查标题、正文/转写、指标、评论字段，记录平台、样本、字段路径、非空值类型与语义。代码别名表出现某名字不等于真实来源证据；价格别名的 24 项通过也不能证明正文别名有效。

同语义且同职责的节点按同一确认集合和有效值语义计数：首次/重试证据上限一致，复核/最终守卫的正文与评论集合一致；不要求所有节点共用一张总表。候选中若调整别名，增加“仅该别名有值、空值、数字（含 0）、列表/字典、冲突、无关同名字段”用例，并检查上限与误删方向。

无真实样本时输出差异表并标“影响待确认”，保留现状，不扩表/删表；这仅限制 D4 的修复结论，不阻塞 D1–D3。

命令形态为 `python3 <脚本> <对应冻结脱敏JSON>`，不得给搜索回放传评分图。首轮同时跑旧基线与候选；新 schema 需要增加 scope/price_basis 或替换 helper 调用时，保留旧输入、旧输出与迁移映射，**业务预期不变**。旧函数的 32 项按语义覆盖迁移，不能机械要求已删除函数继续存在；需要自然语言理解的部分移入模型样例并明确尚未运行。

旧 final-status 的差异逐条对照已确认业务决定：过时断言才可更新，发现真实回归须修复；无法解释则该路径不可验收。不得通过删测试、补造字段值或降低断言制造全绿。新增 T8 同时覆盖首次和重试真实代码，以及写方 schema 到读方的完整链路。

### 7.3 预设验收与调用停止条件

| 层级 | 样本与判据 |
| --- | --- |
| 代码 | P0：T1–T3/T8；P1：T4/T5/T6/T7/T9；全部适用保护用例通过。遗漏条件、已验证硬 FAIL 仍推荐、错误 PASS、缺证混合句放行任一出现即不通过 |
| 草稿模型筛查 | 最少 5 个冻结场景覆盖净价/普通报价、否定/双重否定、缺证混合句，每场景同输入跑 5 次；先核 schema 完整性和预先标注的正确行为，再看分布 |
| 扩大重复 | 初筛有结论翻转且无法由明确缺陷解释时，才考虑 15 位冻结达人各 5 次；两平台分别报告。记录“任一次偏离多数结论的达人数/15”，≤1/15 仅为稳定性参考，不是正确性证明 |
| 真实 E2E | 每平台完成一个按现行早停规则自然结束的需求与最终表交付；不为凑满 15 人继续评分。人工复核至少 5 位/平台，不足 5 位则全查并说明样本限制；强制覆盖可取得的硬 FAIL 与 UNKNOWN |

所有模型/真实调用须在获授权的目标、预算内；数量是计划默认采样方案，不是本次运行授权。初筛失败先定位，不自动扩大调用；扩大样本若超授权预算则保持待验收。人工复核记录逐条件真值/未知与理由，不能把稳定地判错视为通过，也不能用 5 人抽查声称整体“推荐准确率”达标。

不稳定性样本可复用既有“悦己（湖南特产）”记录，但其历史两次输入并非逐字一致，不能据此归因模型随机性。重跑须冻结需求、平台、原生证据、截断结果、模型与参数。

### 7.4 真实交付验收

检查 run 的 `sys.workflow_id` 指向目标 published ID，并单独核对该版本的服务端 hash；记录需求/平台/达人归属、各节点结果及最终 Excel。D1 的 FAIL/UNKNOWN、D3 的缺证说明必须在用户实际看到的列中正确呈现，不能以 Dify JSON 正确替代 Provider 导出与宿主交付验收。

合成、草稿模型和真实 E2E 分开报告。实际样本未触发的分支只算离线覆盖；运行未命中新版本或没有真实产物时，不宣称发布后验证通过。

## 9. 发布与回滚

1. 执行时核对目标评分 app、环境、当前 published ID/服务端 hash 和草稿 hash；保存本次候选涉及部分的差异。若草稿被并发修改，重新读取并合并，不能覆盖他人成果。
2. 保存**发布前版本**的可恢复备份与脱敏审阅副本；候选 hash 不等于备份可恢复。凭据值不导出到审阅文件、日志或仓库；确需同步环境变量时使用现有凭据机制并仅在内存保留，发布前核查操作脚本副作用。
3. 成套更新评分图写方/读方后整图发布；发布后回读 ID/hash 并运行第 7.4 节。只有运行绑定正确、真实结果通过才算完成生产行为验收。手扒图不随评分修复发布。
4. 已验证硬 FAIL 仍推荐、解析/评分错误激增或实际版本不符时，停止新增验证调用，保存证据；按已有回滚授权恢复发布前备份，否则提交具体回滚差异等待决定。不固定回到第 2 节历史 ID。
5. 整图回滚同样须核对发布结果与必要烟测；不把修改单节点草稿当作已回滚。发布、回滚、创建需求、搜索/补全/评分依用户已明确的授权范围连续推进，不重复确认已授权步骤。
6. 本计划不升插件版本、不打包、不安装、不提交或推送 Git。后续若修改仓库代码，执行项目要求的 lint/typecheck/test/smoke；纯计划编辑使用链接、事实引用、状态与差异检查。

## 10. 残余风险与不阻塞的未知项

- D1：没有同口径真实净价证据时只能 UNKNOWN；不新增数据源、不猜公式，保留“待确认”的当前业务语义。
- D2：结构化 verdict 仍可能被模型误判，必须以人工标注场景检查，不能承诺语义全确定。
- D3/D4：缺证类别初始覆盖有限，别名来源不足可能导致计数偏低；报告支持的类别及未验证平台字段。
- 真实搜索参数、跨工作流关联、Provider 的字段持久化能力未知时，分别记录证据缺口，不强行补齐或并入 P0/P1。
- 授权或真实样本不足时，交付可审阅的候选/离线证据并明确未验收层级；不将计划批准当作发布或付费调用授权。
