## 1. 结论与范围

保留现有插件、Dify、Provider 和宿主原生补全的架构，不新增 Agent 框架。优先修复三类问题：

1. **需求事实不一致**：用户澄清已经保存，但搜索或评分读取的需求文本没有包含它；不能让三个工作流各自重新猜一次需求。
2. **搜索目标与检索方式错位**：用户要的是符合身份与长期内容定位的达人，当前路径可能主要召回“发过某类商品笔记”的账号。传参正确是必要条件，不等于搜索准确。
3. **评分与计数边界不一致**：确定性核验存在可执行缺陷；内容匹配、硬条件失败、商务未知、复核失败没有形成一致的交付和计数契约。

目标流程采用 **梯度候选池（10 人→30、20 人→50、50 人→100）、搜索阶段自动调整检索表达、每批最多 20 人补全评分、推荐达标即停**。梯度上限是增加筛选余量，不保证搜索一定满额，也不保证最终推荐足量。

本次目标主要是手动拓展；共享需求解析、评分和历史字段适配的变更须回归询价机构分支。机构回收仍全部补全后评分，不引入手动拓展的分批早停。

不做：重写整个 Hook、重新启用遗留 Browser 工具、新建持久化任务账本、全局缓存、通用多 Agent 编排、批量迁移历史需求、自动升版或发布。

## 3. 搜索准确性的核心假设

将需求分成三层，而不是压成一个商品关键词：

| 层次       | A 的示例                  | 用途                             |
| ---------- | ------------------------- | -------------------------------- |
| 账号资格   | 男博主、粉丝 5 万至 20 万 | 候选资格核验；平台支持时直接过滤 |
| 账号定位   | 男装、商务/职场或潮流穿搭 | 选择检索入口、关键词与召回排序   |
| 商品与场景 | 衬衫、具体内容合作要求    | 判断已有作品和本次合作的相关性   |

优先验证的假设是：**商品关键词驱动的笔记召回不足以代表目标账号定位，导致有限候选池的前段有效密度过低。** 当前搜索要求“取一个尽量简短的词”，可能加剧身份和定位信息的丢失；这仍是待验证假设，不是唯一根因。

检索设计需区分“按账号定位找人”和“按作品证据找人”，但不能未经能力核验就把 `searchType` 改为任意值。排序、翻页、去重时机和截取位置同样影响前 50 个账号的质量。

反证条件：固定账号、时间窗口、用户条件和数量后，原入口也能稳定返回高质量候选，而改善仅来自恢复性别或粉丝过滤，则应降低该假设的优先级，不继续扩建检索策略。

## 4. 目标 Agent 流程

```text
用户原始需求 + 当前有效澄清
  -> 按当前平台解析，内部复核；确有缺项或歧义时一次问齐
  -> 澄清改变了解析输入：合成有效全文，重新解析并复核
  -> 保存独立 requirement
  -> 选择字段，原样展示 URL 并结束本轮
  -> 用户为当前 requirement 提交字段页并回复“好了”后继续
  -> Provider 执行有限的多轮召回
       原条件 -> 同义词/检索表达扩展 -> 去重 -> 核对实际参数
       用户明确修改业务条件：结束旧轮，按新需求回到解析及字段选择
       达到 5N，或策略/资源预算耗尽后，返回当前真实候选池
  -> 受控保存并归一化一份 links CSV
  -> ypscan_summarize_manual_scores 返回当前批（首批 min(20,N)，之后每批最多20人）
       原生补全 -> 当前批 file_bridge -> 评分 -> 保存 manual_score_batch
  -> 再汇总；先核对当前批评分完整性，再累计有效推荐人数
       达到 N：交付并停止
       未达到 N 且还有候选：下一批
       候选耗尽：交付真实结果，复核原因，必要时请求条件放宽
```

上述多轮召回是目标能力。当前 `manual_source_creators` 只接收 requirement ID，不代表重复调用会换词；不得用试调、伪造参数或反复建需来模拟这项能力。

### 4.1 一份有效需求，多个明确用途

- 原始用户证据保留在已有会话和 `originalBrief` 中；`originalBrief` 继续保留最初完整原文，不为本次设计新建全文历史存储。
- 手动拓展首次澄清后与放宽重建后，都形成应用全部当前有效答案的当前平台完整需求文本；解决同字段冲突，不只在旧文本末尾追加相反条件。不得混入另一平台条件或把解析出的检索区间反写成用户原话。
- 若当前有效全文与最近一次成功解析的 `demand` 不同，先用该全文重新解析、复核，再创建 requirement；若已经相同且解析有效，不增加一次无意义重解析。`demand` 与保存的 `rawMessagesJson.original` 必须一致，`parse_outputs` 全量替换为该次输出，`clarifications` 保留最新有效答案；已回答的问题不重问。重新解析仍重复同一明显错误时，按现行 Skill 停止自动重试。
- Provider 手动拓展搜索和评分读取上述同一份有效需求；分别核对工作流入口的真实 `demand`，仅看落库字段不能证明已传导。数值及身份事实与来源可在工作流内部结构化，仅在接口确需时向外增加字段。
- 询价机构保留现行“未改写原文 + clarifications + 顶层参数”的放宽表示，不因共享解析或评分组件而套用手动拓展全文替换规则。其评分需要由 Provider 按该分支已确认条件组装有效需求，保留原始证据；该组装路径尚待核实。
- 明确区分用户条件与检索策略。关键词变化不改用户原意；检索价格浮动不回写成用户硬条件，也不能再次放宽一次。
- 缺少必需报价或出现歧义时按现有复核规则处理，不能靠删除字段绕过当前前置要求。

## 5. 5 倍候选池与搜索阶段调整

### 5.1 数量与停止语义

设用户需求人数为 `N`，候选池目标为 `5N`，单批上限保持 20。至少区分原始链接数、去重候选数、补全成功数、有效评分数和有效推荐数，不能相互代替。

- 候选以当前 requirement、当前平台、稳定 creator ID 去重；搜索阶段已有证据明确违反硬条件的账号不用于凑池。只有链接、缺少资格资料的账号标为待核验候选，不宣称合格。
- 搜索按去重后的真实候选数判断是否达到 `5N`，不能只把状态查询 `num` 从 `3N` 改成 `5N` 就宣称 Provider 搜够了。
- 先结束本轮候选池构建，再开始当前链路的补全评分。首版优先由 Provider 返回一份合并去重后的候选文件，避免改造插件为多文件实时追加池。
- 当前批评分、保存、汇总结束后，累计有效推荐至少 `N` 即停止，不启动下一批。不截断当前批评分行，也不丢弃不推荐行。
- 早停表示“找到足量候选”，不是“评完全部 5N 后选出全池最优 N 人”。不能作后者的交付承诺。
- 50 人示例：首批 `min(20,N)=10`，不足时之后每批最多 20；第一批已有 10 人有效推荐、目标 10 人时，剩余 40 人不再补全评分。
- 5 倍要求平均约 20% 的合格率才在期望上足量，3 倍约需 33%；这不是概率保证，关键词相关性和样本偏差会使结果波动。

### 5.2 自动扩检与真正放宽分开

此前讨论希望将补量和自动放宽前移到搜索阶段。本方案先把不改变合格标准的检索表达调整纳入目标自动扩检；真正业务条件放宽的前移仍需明确新触发判据，不能由“未满5倍”推导。现行 Skill 的复核、放宽顺序与授权规则继续适用：

| 操作                                     | 建议处理                                                     | requirement 与评分口径                                            |
| ---------------------------------------- | ------------------------------------------------------------ | ----------------------------------------------------------------- |
| 同义词、词序、同一账号定位的不同检索表达 | 纳入有限的自动搜索策略                                       | 不改变 requirement 业务条件；按原需求评分                         |
| 更宽查询词或支持的其他检索入口           | 可以扩大召回覆盖；仍保留原资格与内容判断                     | 不把新增召回范围写成用户已接受的合格类型                          |
| 调整价格、粉丝、返点或减少非核心人设限定 | 只执行现行规则允许且已授权的范围；不从笼统“自动放宽”推导数值 | 属于业务条件改变，重新解析、复核、创建 requirement 并重新选择字段 |
| 参数错误恢复为用户已确认值               | 纠错，不是放宽，不重复请求同一条件确认                       | 核实错误层；不能承诺盲目重跑可修复后端偏差                        |

候选未满 `5N` 不等于不能完成 `N`：有真实候选时默认先评分，汇总终态不足后先交付、复核，再按 Skill 提出放宽；零候选终态按状态工具卡直接复核和建议，不创建空表。不得仅因未满候选倍数提前启动数值放宽。用户主动明确修改条件时按需求修改流程执行，不要求先评完旧池。

若要把“有候选但尚未评分”设为新的自动放宽触发点，须作为单独业务变更明确判据并同步 Skill；首版不引入。平台、模式、品牌、数量、截止时间、内容形式、主达人类型等禁止自动放宽项保持不变；取消明确身份资格只能来自用户明确修改。用户主动修改条件或切换功能时，按现行规则撤销此前自动放宽，保留仍有效的人工澄清。

同一有效 requirement 内可合并不同查询轮次；一旦业务条件改变并创建新 requirement，不混合旧池、旧分数或旧文件。不为省事绕过字段页和来源校验。

### 5.3 搜索耗尽与故障

“直到搜满”不能是无界循环。有限策略至少覆盖三种结束原因：达到目标、允许的策略/资源预算耗尽、真实故障或条件无法落实。

- 在实验前固定每轮取数上限、最大策略尝试次数及低增益停止判据。具体数值尚未确定，须作为启用多轮召回前的验收前提。
- 观察每轮新增去重候选数；重复账号不算增量。少量重复查询不应无限延长任务。
- API 超时、登录失败、参数未生效不等于候选耗尽；如实报告，不能借故障触发条件放宽。
- 保留现有任务轮询上限与恢复规则；“换关键词的搜索轮次”不同于“同一个任务的状态轮询次数”。
- 候选池不足时允许按真实人数进入评分；零候选则报告无结果，不伪造交付文件。
- 有补全成功但评分缺行时仍先处理 `await_scores` 或报告阻塞，不以换批、重评或换词绕过问题。

### 5.4 候选顺序

早停使候选顺序直接影响结果。首版保留可解释、稳定的 Provider 顺序；若已有可信检索相关度或作品证据可用于排序，则单独评测后启用，不能在补全前凭空生成“质量分”。不同查询结果如何合并与排序须有确定规则，不能让最先返回的宽泛查询独占前 20 位。

## 6. 评分、复核与推荐计数

### 6.1 修复确定性核验

保留现有归一化和校验节点，不删整段核验。至少补齐：元/千/k/万/w、上下界、开闭比较符、粉丝区间、当前平台报价字段、内容形式及冲突字段处理。

本地评分导出的 `score_json` 与 `score_retry_json` 都内嵌同一核验代码，当前仅 `ATTEMPT` 不同。两个入口必须使用相同修复并各自回放；只改首次节点会在重试成功时重新引入缺陷。另查 `extract_images` 的资料归一化是否已丢失单位、别名或冲突证据，再由 `final` 统一消费核验结果，不能只修末端文案。审计结论（2026-09-09）：`extract_images.evidence_bundle` 只做结构化字段解码、长文本/列表截断和字符预算裁剪，标量字段（粉丝数、报价）按原键保留；`score_json`/`review_json` 直接消费该 `evidence_json`，单位（万/w/k）、别名冲突和缺失字段均已验证。证据被字符预算裁掉时确定性核验按缺失返回 UNKNOWN（fail-closed），不会误判 PASS；已在 `scripts/replay-dify-score-workflow.py` 增加 4 个 `extract_images → score_json` 证据链回放。

不要继续对自由文本取第一个数字作为通用阈值。优先复用需求解析已有的数值事实形态，在评分边界形成明确的字段、比较符、数值、单位、来源与适用范围；若仍由评分解析产生结构化条件，必须对照同一有效需求验证证据，不能形成第二份独立业务真相。

- “粉丝10万，报价5000以内”不能把 10 万当报价上限。
- 多个报价别名冲突不能默认取最小，也不能简单规定任一值超限即淘汰；先核实报价形式、来源和有效期，无法确定则显式冲突/待确认。
- 粉丝或价格缺失不等于 0；不支持的字段不等于无限制。
- 赛道内部限定只核验对应赛道；OR 类型不能改为同一达人必须全部满足的 AND。
- 文案和分数不能掩盖已确认的身份或资格失败。A 的问题不能仅靠降低综合分修饰过去。

### 6.2 推荐与计数的目标口径

以下是拟实施契约，不是对现有输出能力的描述。保留“推荐表示候选资格”的含义，同时把达人不合格、资格证据不足和系统评估失败分开：

| 状态                                                          | 分数与展示                                       | 自动计数                           |
| ------------------------------------------------------------- | ------------------------------------------------ | ---------------------------------- |
| 有效评估且内容、类型与明确资格均通过                          | 展示推荐及真实依据                               | 计入去重有效推荐                   |
| 已确认违反不可协商条件，或有效评估未达到内容/类型阈值         | 展示不推荐，保留可用分数与失败证据               | 不计                               |
| 内容与类型匹配，仅返点、档期等待协商商务信息未知              | 可展示候选推荐，逐项标待确认，不宣称商务全部落实 | 在有效评估及复核通过时计入候选推荐 |
| 明确资格所需证据缺失或冲突，如要求男博主但无法核实博主性别    | 展示待核实及缺失证据，保留可用内容分             | 不计；不能把资格未知归入商务待确认 |
| 评分失败、必需复核未执行/失败，或复核与最终结论仍有未解决冲突 | 展示系统失败/待复核及原因，不包装成达人不合格    | 不计；不使用初评推荐触发早停       |

“必须核实后才入选”与“后续可协商”的划分须来自有效需求和明确业务契约；不能仅按字段名把价格等条件全部移出硬约束。`requirements_complete` 保留为诊断信息，不单独决定计数。原有内容/类型分数阈值不在本次调整；已确认硬条件失败始终优先于模型高分。复核 `verdict` 不直接覆盖程序阈值：先验证其等级、证据和结论是否一致，无法消解的矛盾进入待复核，不只删相反文案，也不再加一层任意模型裁决。

复用已有 `evaluation_status`、`score_valid`、`recommendation_scope`、`manual_review_completed` 及核验结果表达上述语义。自动计数须同时有可信身份、明确推荐结论、有效评分和有效复核证据；`review_failed + score_valid=true + 推荐` 这种组合不能计入。内容分可用不代表推荐资格已核实，不能只靠一个 `score_valid` 兜底。

Provider 必须给出状态到 Excel 的实际映射和样表，验证必需计数信息不会因用户未勾选展示列而丢失。再由汇总器按明确列名或已确认别名读取；不得解析推荐理由猜状态、发明线上列名，或仅在 Dify JSON 增加状态就声称插件已受保护。评分、导出和汇总器配套完成前，不启用新的自动计数口径。

### 6.3 行完整性、有效推荐与早停

评分行是否返回、该行是否有效、是否推荐是三个不同判断。目标调度顺序固定为：

1. 先完成现有来源、requirement、平台、身份、模板和冲突校验；未知状态或未知结论停止，不能猜测。
2. 当前批补全成功者缺评分行时，返回 `await_scores` 并附明确标注的阶段性 `progress`（不代表最终汇总，已保存的单批表也不是最终表）；任务仍在跑时只等待当前已提交任务，已终态则报告 `pending_score_author_ids` 并停止。即使已有 `N` 位推荐也不能越过此检查。修复当前 `reached || exhausted` 优先于 `pendingScores` 的分支顺序，并增加“N=10、成功20人、仅返回19行且已有10位推荐”的回归样本。
3. 已返回、状态可识别的失败/待复核行算作已返回行，不计有效推荐，不自动重评；否则把失败行当缺行会永久卡在 `await_scores`。若 Provider 无法返回可识别的逐人失败行或状态，先报告阻塞，不自行合成评分行。
4. 当前批行齐后，按第6.2节去重计数：达标交付；未达标且有候选则进入下一批；候选耗尽则交付已有真实结果并说明缺口及待复核人数。

全部已返回评分行继续参与完整性判断，沿用模板和来源，不截断当前批或删除失败行；综合分为 0 的评分行不写入最终表，按 `excluded_zero_score_count` 说明，不按缺行处理。若契约允许失败行无有效数值分，需同步明确汇总器的读取与排序规则：可用分数照常排序，无可用分数的行保留状态并置后，不伪造 `0` 分为有效评估。推荐人数由程序计数，Agent 不看理由估算。

## 7. 历史字段兼容

原则：**入口兼容旧形状，内部使用明确语义，出口适配现有消费方；不能把含义不明强行包装为兼容成功。**

| 边界             | 沿用的实现位置                           | 要求                                                            |
| ---------------- | ---------------------------------------- | --------------------------------------------------------------- |
| 需求输出         | 需求工作流的“旧版输出格式适配”           | 保留现有顶层字段；数值事实在内部处理，非必要不扩展 Provider API |
| 插件到 Provider  | `src/contract/registry.js`               | 模式别名、平台别名、JSON 容器和区间格式集中归一化；不散入各流程 |
| 达人资料进入评分 | 评分工作流“归一化达人资料”               | 列名、单位、报价形式映射一次；保留缺失和冲突，禁止跨平台兜底    |
| 评分表进入汇总   | `manual-score-summary.js` 的表头与行解析 | 精确列名/已确认别名、身份、状态和结论处理；不解析理由猜状态     |

必须保留或新增回归保护的情形：

- 八个 Dify Label、抖音 L2=植入/L3=定制、小红书不使用 L3、字符串区间及当前 Provider 模式兼容值不被顺手改掉。
- 历史粉丝 `[1,999999999]` 按既有规则归一为 `[0,999999999]`；明确量级描述仍先澄清。
- 历史价格区间不能反推出单价原意或硬下限，不重复执行 0.7/1.2 或 0.5/1.2 扩展。
- 列名别名同时存在且冲突时停止猜测；同一批内/跨批模板和列配置一致性校验继续生效。
- 新口径下，历史 Excel 缺少必需状态时保留原文件并说明无法按新契约计数，不将缺失默认成通过，也不自动重评。新旧格式的识别必须依据已验证的 Provider 模板或契约证据，不凭文件日期或列数猜测；无法可靠区分时不启用新计数。旧 Provider 直接返回 Excel 的兼容交付仍按下一条处理，不混入新分批早停。
- 旧 Provider 直接返回 Excel 的兼容交付路径保留，但不能宣称它完成了新 5 倍召回或新增评分核验。
- 已开始的 3 倍任务不能因插件升级被误当成已获取 5 倍池。首版在没有进行中任务时切换版本，不迁移任务、不新增持久化策略账本；Gateway 重置后来源登记缺失仍按现行规则停止，不能声称可凭旧文件续跑。
- 不批量重写历史记录、不跨 requirement 拼池、不用本地脚本绕过来源登记恢复历史任务。
