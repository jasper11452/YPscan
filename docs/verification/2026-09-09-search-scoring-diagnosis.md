# 2026-09-09 搜索与评分链路只读诊断

> 状态：截至 2026-09-09 的只读诊断记录。当时未修改 Dify、Provider 或真实业务数据，也未发布或部署。本记录把已验证事实、建议设计和未验证边界分开；不把建议写成线上修复结果。2026-09-10 的后续处置见文末。

## 结论

用户已明确验收顺序：先判断达人类型是否符合，再在类型符合的候选中核对数据；核心目标是最终能否找到并推荐足量合格达人。档期是否落库不是本次主要判据。

本次最直接的数量损失发生在评分工作流：`西装控 Alan` 的类型和内容相关度均为 3，粉丝 108472，视频报价 12000 元；评分结果因 H5“报备图文/视频报价2万-3万元”被标为 `FAIL`，最终为 `hard_constraint_fail / 不推荐`，综合分仍为 73。这个事实证明了“报价条件被当作硬区间”会淘汰类型命中的候选；它尚不能证明 2 万是错误的最低价，因为用户是否确认了最低价语义仍未决。

评分 prompt 中“价格、粉丝、播放、互动、返点、档期、画像只作参考，不参与档位”与 final 的硬条件判断本身不必然矛盾：前者可以定义相关度分档，后者可以定义硬准入。语义风险/待核问题是：H5 当前被赋予了硬区间语义，而用户只选择了“2 万–3 万元”报价范围，未明确“低于 2 万不得入选”。

## 报价语义不能擅自确定

“报备图文/视频报价 2 万–3 万元”至少有三种待确认含义：

| 解释        | H5 处理                                                                      | Alan 预期                                  |
| ----------- | ---------------------------------------------------------------------------- | ------------------------------------------ |
| 目标价/偏好 | 放在 `secondary_conditions` 或现有 `business` 信息中，标记低于目标；不硬淘汰 | 类型和内容合格时仍可进入候选，显示价格偏离 |
| 硬区间      | 只有用户明确“必须在 2–3 万”“低于 2 万不要”时才放入 `must_have`               | 12000 元 FAIL，不推荐                      |
| 最高预算    | 用户明确“最高 3 万/不超过 3 万”时只核验上限                                  | 12000 元 PASS                              |

原文“中腰部KOL：2.5W10位”也不能自行拆成粉丝量或报价。解析器若无法确定，保留原文并按现有复核规则澄清；不能用解析出来的检索区间反推用户原意。

## 最小修复设计

不新增通用条件实体或必选 schema，复用 `target_tracks`、`must_have`、`must_not`、`secondary_conditions`、`constraint_results` 和现有 `business` 字段。

1. 在评分解析节点中，只把有明确硬标记且适用于单个达人的条件放进 `must_have`；“2–3 万”没有最低价/最高价/必须区间语义时不要自动生成硬失败条件。类型仍由 `target_tracks` 与 `track_logic`表达，不重复伪装为 `must_have`。
2. 在 `score` / `review` prompt 中明确顺序：先依据简介、身份和实际作品判断 `type_relevance`，标签只作线索；类型不符合时不推荐。类型通过后再核验 `constraint_results` 中的用户明确条件。价格、粉丝等不影响相关度档位，但其明确硬条件仍可在准入层生效。
3. 在 `final` 中保持现有硬条件失败、次要条件和未知的分流：明确硬条件 FAIL 才是 `hard_constraint_fail`；`secondary_conditions` 的 FAIL 只作参考；证据不足为 UNKNOWN/待核实，不能改写成 FAIL。类型未知应待核实且不计入有效推荐，系统失败也不能用初评推荐触发早停。
4. Provider 仍保持 `manual_source_creators(requirement_id)` 入口。搜索返回时应提供或内部记录实际关键词、粉丝上下限、内容标签和性别筛选，并与当前 requirement 逐项比对；本次证据只证明 `kwGender` 未出现在 batch600/606 实际参数，不证明 Provider 一定支持或一定丢弃该字段。

| ----------------------------------------- | ----------------------------------------------------------------------------------- |

“类型先、数据后”这里指决策顺序，不要求凭空新增一套综合分。若业务确实要在类型通过后按表现数据排序，必须另行定义使用哪些数据和权重；当前 Dify 评分只对类型/内容相关度打分，不能声称已经实现性能数据排序。
